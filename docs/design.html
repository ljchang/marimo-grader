§1Decisions in brief

Draft 1 asked for an audit of MoGrader before any infrastructure work. That audit is done (§2) and it changes the shape of the project in one important way: MoGrader's grading engine is excellent and reusable, but its server, identity, and gradebook layers are built for a single course with shared-secret tokens. The recommendation is to depend on the former and replace the latter.

  • D1
    Use MoGrader as a Python library, not as the server.Import its authoring markers, notebook generation, check runtime, sandboxed autograde runner, and integrity checks. Do not fork its HTTPS server, hub, or SQLite gradebook. Contribute small upstream PRs where the engine needs a hook.
  • D2
    One new FastAPI service owns identity, tenancy, submissions, grades, and audit.PostgreSQL from day one. Immutable per-attempt submissions. Server-side authorization on every route. A worker container runs autograding.
  • D3
    Dartmouth SAML in the browser; a device-style handshake for notebooks.The notebook never touches credentials or SAML. It requests a login code, the student signs in through Dartmouth in a normal browser tab, and the notebook receives a short-lived token bound to the verified NetID.
  • D4
    The notebook snapshot is the artifact; the question is the grading unit.Every Submit uploads the whole notebook and names the question being submitted. This gives MoGrader's runner what it needs (hidden-test reinjection, cell-hash integrity) while grades, attempts, and feedback stay per question.
  • D5
    Instructor and student UIs are one Svelte 5 single-page app served on the same origin as the API.marimo stays in the notebook where it belongs. The dashboards need fast filtering, keyboard-driven grading, and a triage view that updates as submissions land; a purpose-built reactive frontend does that better than a mounted marimo app. Rendered student notebooks come from the worker as HTML artifacts, so the frontend never runs Python.
  • D6
    Generic core, DartBrains as the first tenant.The service and its client library carry no course-specific code. dartbrains-tools gains a thin module that preconfigures the server URL and course and exposes the student-facing widgets.

§2What the audits found

Dartmouth SSO, as implemented in pbs_knowledge

The working implementation on dartmouthpbs.org is SAML 2.0 against Dartmouth's Shibboleth IdP, not OIDC or CAS. The details that matter for a new service:

  • IdP entity urn:mace:incommon:dartmouth.edu, SSO at https://login.dartmouth.edu/cas/idp/profile/SAML2/POST/SSO, logout at https://logout.dartmouth.edu. Duo runs inside the IdP; the app does nothing for MFA.
  • NetID comes from eduPersonPrincipalName (split on @, lowercased), not from NameID. Affiliation from eduPersonAffiliation. Display name, given name, and surname are available.
  • IdP quirks that must be replicated: the assertion is signed, the response envelope is not; allow about two minutes of clock skew; disable RequestedAuthnContext; sign the AuthnRequest.
  • The SP metadata file, the IdP metadata with its signing certificate, and the email template used to register with Dartmouth IT are all reusable as-is. A new SP entity (for example https://grader.dartbrains.org) must be registered with IT; budget a week or two of turnaround.
  • Do not port the Firebase custom-token session or the localStorage token. Use an HttpOnly session cookie for web UIs and a separate short-lived bearer token for notebooks.

MoGrader (jameskermode/mograder, 0.3.3, MIT)

Single-author, actively developed (36 releases since March 2026), Python 3.11+, tested on three platforms. Its pieces, and their fit:

Classification against draft 1's requirements: inherited unchanged are the check/submit distinction, hybrid grading, and the autograde mechanics. Small extensions are stable question IDs (label-prefix convention plus cell hashes), a TA role, the triage dashboard, and Canvas columns. Substantial new work is SSO-bound identity, multi-tenancy, attempts in the database, rubrics, PostgreSQL, and audit logging. That list is exactly the boundary in D1.

§3MoGrader as engine, not server

Forking a 4,000-line CLI that ships a release a week means carrying merges forever. The parts we need are importable modules with stable inputs (a notebook file, a course directory layout) and outputs (a JSONL sidecar, a results dict). The parts we would change most are the ones we would not use anyway.

Import from mograder

  • mograder.grading.cells: generate student notebooks, compute cell hashes
  • mograder.runtime.check and Grader: in-notebook checks
  • mograder.grading.runner and integrity: autograde a submission in a sandbox
  • mograder.grading.feedback: annotated feedback HTML

Build new

  • FastAPI service: auth, tenancy, submissions, grades, audit, exports
  • PostgreSQL schema (SQLAlchemy 2, Alembic)
  • Worker that materializes a submission into MoGrader's expected layout and runs the runner
  • Client package with the login handshake and submit widget

Borrow ideas from mograder

  • Grader app navigation (prev/next, keyboard flow, feedback minimum) informs the Svelte grading view; no code is reused
  • Feedback HTML export runs in the worker and becomes the rendered view the frontend embeds

Contribute upstream

  • Pluggable transport factory (currently hard-coded to https and moodle)
  • Authorization header on the injected submit cell
  • Per-question grouping of check results in the sidecar
  • Runner entry point that takes paths explicitly instead of a course directory
Risk to watch

MoGrader's runner assumes the on-disk layout submitted/<assignment>/<user>.py and reads instructor sources from the course directory. The worker will materialize this layout per job in a temp directory. Pin the mograder version in the worker image and run the engine's own test suite against each bump.

§5Identity and the notebook login handshake

Two kinds of principal talk to the service, and they authenticate differently.

Web sessions (instructor, TA, student portals)

Standard SAML SP flow: GET /auth/login redirects to Dartmouth, POST /auth/saml/acs validates the assertion, upserts the user by NetID, and sets an HttpOnly, Secure, SameSite=Lax session cookie backed by a server-side session row. Roles are never taken from SAML; they are looked up per offering from the enrollments table (§8).

Notebooks (the hard case)

The notebook kernel may be in a MoLab container, in Pyodide inside the student's browser, or on a Discovery compute node. None of those can complete a SAML redirect, and the notebook must never see credentials. The shape that works everywhere is the OAuth device authorization flow, run by our own server.

  • Where the HTTP calls originate. The widget is an anywidget, so its JavaScript runs in the student's browser regardless of where the kernel is. Run the handshake and the submit request from JavaScript. This is the one path that behaves identically in WASM, MoLab, and Discovery, and it sidesteps the question of whether compute nodes have outbound internet. The kernel's job is to assemble the payload and hand it to the widget through the anywidget model.
  • Token shape. JWT signed with an Ed25519 key held by the server. Claims: sub (NetID), scope: notebook, exp (8 hours), jti for revocation. No refresh token in v1; when it expires the button says "Sign in again" and the handshake takes one click plus Duo.
  • Where the token lives. In the widget's in-memory state, mirrored to the kernel so submit() can be called programmatically. Optionally cached in localStorage on the notebook's origin so a page reload does not force a new Duo prompt within the 8 hours. It is never written into the notebook file.
  • CORS. Allowlist the origins a notebook can run in: https://dartbrains.org, https://molab.marimo.io, the Dartmouth Open OnDemand host, and http://localhost:* for local marimo. Everything else is refused.
  • Popup blockers. The verification tab must be opened synchronously from the button's click handler. The widget also shows the URL and the user code as text so a student can open it manually.

§6Submission model

Draft 1 asked for per-question submission. MoGrader grades whole notebooks, and it needs the whole notebook to reinject hidden tests and verify cell hashes. Both are satisfied by making the notebook snapshot the stored artifact and the question the unit of attempts, scores, and feedback.

Check versus Submit

  • Check runs entirely in the kernel through MoGrader's check(). It never blocks on the network. If the student is signed in, the widget also posts a small check event (question, check key, pass or fail) so the instructor dashboard can say "38% of the class is failing the design-matrix check." If the student is not signed in, nothing is sent.
  • Submit requires a token. It records an immutable attempt and enqueues autograding. Feedback for autograded questions appears in the widget within seconds; manually graded questions show "Submitted, awaiting grading" until an instructor scores them.

Payload

POST /v1/submissions
Authorization: Bearer <notebook token>

{
  "assignment_version": "glm@3",          # from PEP 723 metadata MoGrader injects
  "question_id": "glm-q03",
  "notebook": "<full marimo .py source>",
  "check_results": [...],                  # sidecar JSONL from this kernel, advisory only
  "outputs": {"glm-q03": {"html": "...", "figures": [...]}},   # optional, size-capped
  "client": {"package": "dartbrains-tools", "version": "0.2.0", "env": "molab"}
}

The server adds, and the client cannot set: NetID (from the token), enrollment, server timestamp, attempt number (next in sequence for that enrollment and question), submission ID, artifact hash, and grading status. Client-reported check results are stored for diagnostics but never used for a grade; the worker recomputes everything.

Attempt policy

Per assignment, the instructor sets: attempts allowed (unlimited, N, or one), which attempt counts (latest, highest, first, or instructor-selected), due date and late policy, and whether checks are logged. These are settings on the assignment, not code in the notebook, so they can change without republishing.

Reading the notebook's own source

The kernel must read its own file to build the payload. In local marimo and MoLab this is __file__ or mo.notebook_location(). In WASM the file lives in the Pyodide virtual filesystem. This needs a spike in all three environments (§15) before the widget is finalized.

§7Data model

  • Immutability. submissions, artifacts, grader_runs, and assignment_versions are insert-only. Application code has no UPDATE path for them; a database role without UPDATE on those tables enforces it.
  • Official grade. The grade for (enrollment, question) is derived from the attempt policy over that student's submissions and their final scores row. Store it in a small question_grades table recomputed by trigger or job, so exports and dashboards do not re-derive policy each time, and so an instructor can pin a specific attempt.
  • Audit. Any write to scores, question_grades, enrollments, or assignment settings inserts a grade_audit row with actor, before, after, and reason. This is the FERPA audit trail and the grading-dispute record.
  • Minimization. users holds NetID, an optional display name from SAML, and nothing else. No email column; NetID plus @dartmouth.edu reconstructs it when an export needs it. Affiliation is used at login for a sanity check and not stored.
  • Retention. A per-offering retention_until drives a job that deletes artifacts and check events after the retention window while keeping question_grades and the audit log. Dartmouth's records policy sets the window; default to five years after the term ends until told otherwise.

§8Tenancy, roles, isolation

The hierarchy from draft 1 stands: platform, course, offering (a term), section, enrollment. Roles attach to an enrollment, so the same person can be an instructor in one offering and a student in another, and a TA's reach is scoped to their sections.

Enforcement is one FastAPI dependency, require(offering_id, roles), that resolves the caller's enrollment and refuses otherwise. Every query that touches student data takes an offering ID from that dependency, never from the request body. Platform admins deliberately cannot read student work; if that is ever needed it should be an explicit, audited break-glass action.

Rosters should almost never be typed in. The import pipeline has one internal shape, a list of (NetID, display name, section, role), and a set of source adapters that produce it. Every import is a preview first: the instructor sees adds, drops, and section moves before confirming, and the confirmation is audited.

§9Assignment lifecycle

  1. AuthorThe instructor writes one marimo notebook using MoGrader markers. Each question is a check("glm-q03: Design matrix", [...]) call plus a marks entry. The label prefix is the stable question ID; the visible title after the colon can change freely.
  2. Publishgrader publish glm.py --offering neuroimaging/2026-fall signs the instructor in via the same device handshake, runs MoGrader's generation to produce the student version, uploads both sources as artifacts, and registers a new assignment_versions row with the cell hashes and the question list parsed from the marks cell.
  3. DistributeThe service serves the student version at a stable URL. dartbrains.org links to it through marimo-book's launch buttons: MoLab, WASM, or an Open OnDemand launcher, as permitted by the assignment's environments setting. The student version already carries assignment_version in its PEP 723 metadata, so the widget knows what it is submitting without any student input.
  4. Work, check, submitStudents iterate with Check, sign in once, and Submit per question. Autograded questions return feedback in the widget; manual questions show their queue status.
  5. GradeThe worker autogrades on arrival. Instructors and TAs score manual and hybrid questions in the grader app. Grades finalize per the attempt policy.
  6. ReviseRepublishing creates version N+1. Old submissions stay bound to the version they were made against and are regraded only if the instructor explicitly asks, with the audit log recording it.
  7. ReuseAn assignment can be copied into a new offering. The copy starts at version 1 in the new offering; nothing in the source offering changes.

§10Grading modes

Deterministic autograding

The worker writes the submission into a temp course directory in the layout MoGrader expects, reinjects hidden tests and the instructor's check cells from the pinned assignment version, and runs the runner under bubblewrap with no network, rlimits, and a wall-clock cap. Results are parsed from the sidecar, grouped by question, and written as a grader_runs row plus an auto_points score. Because the sandbox has no network, any dataset an assignment needs must be pre-cached on the worker volume; the publish step should list required datasets so the cache can be warmed.

Manual and rubric grading

Rubrics are a list of items with points and a description, stored as JSON on a rubrics row and referenced by questions. The grader app shows the student's code and rendered output for the question, the rubric as checkboxes or point fields, and a feedback box. MoGrader's app has the navigation and layout; the rubric panel is new.

Hybrid

total = auto_points + manual_points, with max_points split declared on the question. This is what MoGrader already does with its slider; it maps directly.

AI-assisted suggestions (later)

Model this as another grader_runs kind that writes suggested_points and suggested_feedback on the score row. Suggestions are never final without a human accepting them, and acceptance is audited like any grade change. Before building it, confirm which model vendor Dartmouth has approved for student work under FERPA; sending submissions to an unapproved API is a compliance problem, not a technical one.

§11Instructor dashboard and student portal

One Svelte 5 application, built with runes and TypeScript, served as static files from the same origin as the API. It signs in through the same SAML flow (a redirect to /auth/login and back), holds no token in JavaScript, and talks to /api with the HttpOnly session cookie plus a CSRF header. Role-based routing decides which views a user sees, but every view is backed by an API call that enforces the same rule server-side.

Why not marimo apps for this

  • A grading queue is a keyboard-driven, state-heavy UI: next student, tab between rubric items, type feedback, submit, repeat. That wants local reactive state and optimistic updates, which runes give directly and a kernel round-trip per interaction does not.
  • A mounted marimo app holds a Python kernel per browser session. Fine for ten instructors; awkward for a whole class opening the student portal at once.
  • pbs_knowledge already established a Svelte 5 + Vite frontend with SAML sign-in and role-aware routing. Its auth store and route guards carry over; only the backend session model changes (cookie instead of Firebase token).

How the frontend shows a notebook without running Python

When the worker grades a submission it also runs marimo export html on the snapshot and stores the result as an artifact. The grading view embeds that HTML in a sandboxed iframe with no scripts and no network, scrolled to the question being graded, next to the rubric panel. Students see the same rendering in their attempt history. Nothing in the frontend ever executes student code.

The triage view

The instructor's landing page answers "who needs my attention." Concretely, in this order:

  • Submissions awaiting manual grading, oldest first, grouped by question.
  • Students with no activity in seven days while an assignment is open.
  • Checks failing for more than a third of the class in the last 48 hours, with the check key and its failure message.
  • Autograder failures (timeouts, crashes) that need an instructor to look at the notebook.

Below that, the roster grid from draft 1: one row per student, one column per question, cell states not started, checking, submitted, graded with points, with last activity. A student row opens their attempt history; a question column opens its distribution.

Student portal

One page per offering: assignments, status, grade, and, per assignment, every attempt with its feedback. This is where feedback survives after a MoLab or WASM session is gone. The same page is what the "View feedback" button in the notebook opens.

§12Canvas export

Canvas's gradebook import matches rows on SIS Login ID, which at Dartmouth is the NetID, and needs the assignment column header in the form Assignment Name (12345) with Canvas's internal ID. The instructor exports their current Canvas gradebook once, uploads it to the grader, and the grader emits a CSV with the same student rows and the selected assignment columns filled in. No Canvas credentials are stored, and the LTI path stays open for later. Verify the SIS Login ID assumption against a real Dartmouth Canvas export before shipping.

§14Client library and dartbrains-tools

Keep the generic client in its own small package so any course can use it; dartbrains-tools depends on it and supplies defaults. Working names below are placeholders.

# generic client (works in local marimo, MoLab, WASM)
from grader_client import Grader
g = Grader(server="https://grader.dartbrains.org")   # reads assignment_version from the notebook's PEP 723 block
g.signin_button()          # anywidget: "Sign in with Dartmouth" → device handshake in JS
g.check("glm-q03", [...])  # wraps mograder.check; logs a check event if signed in
g.submit_button("glm-q03") # anywidget: "Submit" → snapshot + POST from JS, shows result
g.feedback("glm-q03")      # latest feedback for this question, or a link to the portal

# dartbrains-tools: the same, preconfigured
from dartbrains_tools import grader
grader.submit_button("glm-q03")
  • The widget is one anywidget class with a mode (sign-in, submit, feedback) so the JavaScript for the handshake and the fetch lives in one place.
  • The kernel side has no HTTP dependency in v1; all network traffic goes through the widget's JavaScript. A Python-side httpx path can be added for headless use (an instructor's publish CLI already needs one).
  • Pin dartbrains-tools and mograder versions in the assignment's PEP 723 block so MoLab and WASM resolve the same versions the autograder uses.

§15Spikes to run before building

Each of these is a day or less and settles a question that would otherwise be discovered late.

  1. SAML SP in FastAPI against the Dartmouth IdPpython3-saml with the pbs_knowledge metadata and quirks. Requires registering the new SP entity with Dartmouth IT, so start it first.
  2. Device handshake from a MoLab notebookanywidget opens the verification tab from a click, polls, receives a token. Confirms CORS, popup behaviour, and that molab.marimo.io lets widget JS reach an external origin.
  3. Notebook self-source in all three environmentsRead the running notebook's own file in local marimo, MoLab, and WASM. If WASM cannot, the student version can embed a copy of its source hash and the widget can fall back to marimo's export endpoint.
  4. MoGrader runner as a library in a containerbubblewrap with no network, a pre-warmed Hugging Face cache, one real DartBrains assignment. Measures grading time per submission.
  5. Discovery Open OnDemandIs there a marimo app in OOD today, and does its proxied origin work with the widget? If not, the Discovery button ships later; the design does not depend on it.
  6. Canvas and Banner formatsOne real gradebook export from a Dartmouth Canvas course to confirm the SIS Login ID and column header assumptions; one Banner class-list download to see its columns; and a check of whether Dartmouth Canvas lets an instructor generate a personal access token.

§16Roadmap

  1. Skeleton (weeks 1 to 2)Repo, Docker Compose, PostgreSQL schema and migrations, SAML login for web sessions, users and enrollments, one course and offering seeded. Spikes 1 to 3 in parallel.
  2. Submission loop (weeks 3 to 4)Device handshake, POST /submissions, artifact store, the anywidget with sign-in and submit, publish CLI. A student in MoLab can submit one question and see "received."
  3. Autograding (weeks 5 to 6)Worker, MoGrader runner integration, results back into the widget. Spike 4 becomes production code.
  4. Instructor and student UIs (weeks 7 to 10)Svelte 5 app: sign-in, triage view, roster grid with Canvas CSV import, attempt history, grading queue with a rubric for one question and the worker-rendered notebook, student portal with feedback, SSE for live status.
  5. Hardening (weeks 11 to 12)Audit log, retention job, rate limits, backups and restore test, security review package for Dartmouth. Canvas export.
  6. PilotOne DartBrains assignment with a real class. Then sections, TA role, WASM, Discovery, AI suggestions.

The MVP checklist from draft 1 maps onto phases 1 to 4. Multi-tenancy is not deferred: it costs almost nothing to have offering IDs in the schema and the auth dependency from day one, and retrofitting it is the expensive path.
